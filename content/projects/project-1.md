# 项目背景

传统作品集要求招聘方自己翻完整站。招聘方时间有限，关心的问题也不一样：有人看从 0 到 1，有人看人工智能，有人看商业结果。

这个项目是一份求职作品集，同时也是我用来证明人工智能产品判断的案例。它不是某家公司的正式任职项目。

# 用户问题

招聘方很难在短时间里，按自己的问题把候选人经历组织起来。固定页面无法针对不同角色给出不同的证据路径。

# 商业问题

如果招聘方获取信息的成本过高，候选人即使有相关项目，也可能在第一轮就被跳过。这个项目要降低「读懂这个人」的成本，同时避免用模型编造经历来换流畅感。

# 我的职责

我负责问题定义、真实性原则、工具边界、知识库结构和验收标准。工程实现由协作完成。团队里没有单独的用户研究或增长职能。

# 问题发现

依据是产品假设和求职场景，不是已完成的招聘方面访样本。因此「招聘方会问什么」目前仍是假设，不是已验证的用户研究结果。

# 核心洞察

不同招聘方不会按同一顺序阅读作品集。与其只做固定页面或站内关键词搜索，不如让模型按问题决定要不要检索、检索哪一段，并把来源交给招聘方核对。

# 产品决策

第一版选择智能体，而不是普通 RAG：模型是大脑，知识检索是它可调用的工具。同时要求：事实必须有证据；推断必须标明；资料不足就承认不知道。

# 备选方案

1. 只做静态作品集网站。
2. 做站内搜索。
3. 每个问题都先搜索再生成的固定 RAG。
4. 引入多智能体或向量数据库。

# 产品取舍

放弃复杂框架、向量库、流式输出和长期记忆。作品集体量很小，当前要验证的是：模型能不能自主找到证据，而不是系统看起来更「人工智能」。

# 最终方案

招聘方在 `/agent` 提问。服务端运行有上限的智能体循环。模型可调用 search_knowledge、get_project、get_profile、list_projects。知识库是本地 Markdown。生产环境只读取 status: published 的资料。回答附带章节级来源。

# 人工智能与技术设计

传统规则或关键词搜索处理不好开放问题、比较和「资料不足」。模型负责理解问题和选择工具；不负责发明经历。错误处理：无有效证据的履历回答会被系统拦截。评估看事实正确率、引用是否支撑结论、幻觉和响应，而不是看是否「像能聊」。延迟、成本和人工介入方案尚未用线上数据验证。

# 最小可行产品

已做：本地检索、四类工具、当前会话记忆、证据 ID、发布状态过滤。故意没做：登录、长期记忆、流式输出、自动评分、完整视觉包装。

# 上线结果

尚未对真实招聘方发布，因此没有投递转化、使用时长或满意度数据。不能把本地开发通过写成已经验证的业务结果。

# 项目复盘

目前验证的是机制能否跑通，不是求职结果。如果重新做，会更早写入真实任职与项目，而不是先用演示数据把 Prompt 调到对假内容很熟。
